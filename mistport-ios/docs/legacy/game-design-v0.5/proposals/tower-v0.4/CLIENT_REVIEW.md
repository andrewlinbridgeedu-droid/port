# 长阶 v0.4 接入审查与扩展约束

本轮接收设计候选数据，不开放正式楼层。原始包保持不变。已在临时目录重跑 audit_tower.py：49 项通过；结果见 audit_results.rerun.json。测试覆盖配置与内存结算模型，不证明实际构筑胜率、动画命中、持久化事务或完整游戏可玩性。

## 用户确认的长期边界

- 内容可以持续追加，每个序列的成长、触发与奖励有边界；当前是三塔各 100 层候选配置，不是自动生成无限层。
- 采用可追加章节清单。章节保存稳定 ID、所属塔/序列、显式前置、楼层列表、规则版本、奖励预算及发布状态。客户端从已发布配置推导末层，不将 100 作为永久上限。
- 旧楼层 ID 和首通权益保持稳定，追加章节不能因改版重发旧奖励。各塔进度和研究独立。
- 序列 9 后续章节以阵容、窗口、目标和机制组合扩展，不继续外推属性曲线；需要更高成长阶段的内容归入序列 8 挑战。
- 校准最多 5 级，基于当前等级计算一次固定增量，不复利，不跨序列作为额外乘区叠加。退款按实际支出记录，退款与属性/快照更新共同提交。该候选机制仍需单独战斗验收。
- 同类天赋/技能/遗落物效果使用共享触发预算；战斗内按既定主体、事件和时间窗口核算，不按效果来源各复制额度。追加内容不得暗中提高现有上限，反击等派生事件须遵循既定事件链限制。
- 每批新增章节独立提交首通与累计奖励预算，不沿用递增奖励公式自动外推到任意层数。

## 当前包与目标的差距

build_tower.py 使用 floor_count=100、range(1,101) 和十章固定预算数组。这适合生成本次冻结候选数据，但尚未实现通用可追加章节系统。正式接入应消费显式章节配置，不把该生成器直接作为无限楼层服务。

49 项审计未验证同类触发共享上限或真实战斗可通关性。reference_rules.py 的胜利是外部注入条件，且不检查 release_enabled；仅可作参考，不能直接作为客户端正式发奖入口。全部楼层仍为 release_enabled=false。

## 制作顺序

1. 完成 P0 五级天赋与真实战斗资源机制接入，完成原最小教会任务/战斗/奖励闭环。
2. 接入章节读取、独立塔进度、可信战斗回执与原子首通结算；先制作守灯 1—20 层。
3. 验收失败/退出无奖、重复回调无重复奖励、存档中断恢复、剧情锁与失败原因区分，以及换构筑后返回原层。
4. 使用专精 30、混合 20+10、15+15 等候选构筑做真实命中回放，分别测试校准 0/1/3/5，记录失败机制。达到验收条件后再开放各章。
5. 三塔前 20 层验证后逐章扩充；101 层及以后需新增设计、预算与测试。

UI 沿用已确认的浅色幻想插画风格：三塔切换、十层章节、默认当前下一层；底部安全区提供敌情、调整构筑、开始挑战。已通关明确标注重打无资产奖励，未发布章显示真实开发状态。
