# 共享服 M0：服务端技术小样 · 2026-09-29

用户 2026-09-29 定：做共享服。按[规划书](../../planning/world-economy-launch-20260928/雾港世界战役与经济系统落地规划书.md)，第一步是 M0 的“服务端技术小样”，放行条件是“一笔共享交易和一场关键战验证可跑通”。交接页下一步第 5 项“服务端账户与可信战斗结算小样”就是这件事。

**结论**：在 Linux 云端跑通了。一个权威服务加一个 SQLite 事务库，用 HTTP 完成了一笔玩家之间的交易，以及一场世界事件公共战（亮灯事件的公共目标）的开票、客户端操作记录、服务器复算和发奖。**这是技术验证，不是上线服务**，也没接进 App（见“还缺什么”）。

## 做了什么

### 1. 规则库：同一份代码打仗和复算（`MPCChurchBattleDriver`）

- 位置：`mistport-ios/MistportCombatCore/Sources/MistportCombatCore/ChurchBattleDriver.swift`。
- `MPCChurchBattleStepper` 每次推进 50 毫秒，并返回表现事件（谁开始出手、何时命中），供 App 按真实时间逐格推进、交给 Unity 播放。`record` 和 `replay` 也走同一个 stepper。
- 覆盖“教会系”战斗：深井塔层、通缉、街头战（城市事件、残余案、街坊）、亮灯公共目标。这些战斗的敌人出手时机由规则决定（首次延迟、出手时长、蓄力）；技能按自动序列每 1.75 秒出一招。玩家能做的选择只有五种：
  - 换目标；
  - 开篡命勋章；
  - 用空白名片挡某个敌人；
  - 用药；
  - 放终极技。
- 客户端交给服务器的是**操作记录**：规则版本（`church-battle-v1`）、战斗编号，以及每个操作发生在第几个 50 毫秒。记录里不带结果，不带配装，也不带背包，这些由服务器自己保存。
- 服务器复算规则：
  - 同一份记录，同一套配装，结果（胜负、用时、血量、用药）逐项相同；
  - 记录里任何一个操作被规则拒绝（例如冷却中再开勋章、药用超数量），整份记录作废；
  - 顺序错乱、战斗结束后还有操作、规则版本不对，也都作废。
- 敌人出手时机和数值调参用的塔层验证模型（`MPCChurchTowerVerificationRunner`）是同一套，没有随机抖动。测试确认两者在 3、10、20 层胜负一致、用时差不超过 1 秒。
- **和 App 还不一致**：App 的教会战斗有几处驱动器里没有的规则，例如敌人死时撤销已出手的攻击、换波清空待命中攻击、Unity 回调触发的取消。逐条差别和搬进规则库的做法见 [Codex 任务单](../CODEX_TASKS_SHARED_SERVER_M0_20260929.md)。

### 2. 服务端（`mistport-server/`）

详见 [`mistport-server/README.md`](../../../mistport-server/README.md)。要点：

- **铜**：发行、转账、销毁分开记账，货币总量恒等于发行减销毁。审计会按账重算每个账户、每个物品批次、每个挂单和票据的托管。
- **物品批次**：塔层掉落记录来源（`tower-drop`＋票据号），交易后来源不变。
- **幂等**：每个写请求带操作号。重复请求返回同一结果（失败也一样），同号不同内容则拒绝。
- **原子成交**：买家的铜、卖家的铜、交易费（5%，默认进城市预算，可配置为真销毁）和货在一个事务里交换。8 个数据库连接、40 个买家同时抢最后一件，只有一笔成功，连跑 8 次一致。
- **战斗票据**：
  - 开战前检查资格（塔层不越级；亮灯公共目标每号一次），从城市预算预留奖励，把带进战斗的药放进托管；预算不够就不开战。
  - 结算时服务器用自己保存的角色复算。打赢才付奖励（塔层掉材料、推进层数；公共目标记 1 点贡献）；打输或记录作废，奖励退回城市预算。用掉的药销毁，其余退回。
  - 每张票只结算一次，30 分钟不结算自动关闭。
- **本地财富带入**（用户已定带进共享服）：每号一次，同一存档指纹只能带一次，上限 12,000（待确认）。指纹由客户端提供，服务器验证不了真伪；这个风险用户已接受。

## 证据（Linux，Swift 6.0.3）

| 项目 | 结果 |
|---|---|
| 规则库全部测试 | 534 项通过（原 526 项＋新增驱动器 8 项） |
| 驱动器测试 | 塔 5/12/30 层录制＝复算；与调参模型一致；亮灯公共目标可打赢并复算一致；10 个通缉、城市事件、残余案复算一致；像 App 一样手动逐格推进，结果、记录和表现事件一致；服务器用自己的配装；非法记录 6 种全部拒绝；空记录结果固定 |
| 账本测试 14 项 | 创世与重开不重复发行；令牌；本地带入（封顶、每号一次、指纹一次、幂等、冲突）；成交（手续费、托管、来源、撤单、不能买自己）；失败回执；手续费销毁；40 人抢最后一件；塔层胜利掉落且只发一次；公共目标先预留后付款；打输不付；强角色录的记录和伪造记录不付；带药托管与消耗；过期退回；预算不足不开战 |
| HTTP 端到端 2 项 | 同一剧本分别走进程内路由和真实 socket：建号 → 运营发测试货和设角色 → 带入本地铜 → 挂单 → 买入（重试不重复、同号改内容 409）→ 开公共目标票 → 客户端打一场并提交记录 → 服务器复算付 12 铜、记 1 点贡献 → 别人冒领 404 → 审计平账 |
| 可执行文件 | `swift run mistport-server` 起在本机端口，用 curl 走过建号、带入（20,000 被封到 12,000）、越级开塔被拒、审计 |

复现：`cd mistport-server && swift test`；规则库测试在 `mistport-ios/MistportCombatCore` 下 `swift test`。

## 选型（2026-09-30 定，用户授权代定）

- **Swift 服务端**：和 App 共用规则库，复算不用另写一套。Linux 可编译运行。
- **Hummingbird 2.17**：Swift 6.0 能编译的最后一版。换到更新的 Swift 后可以升级。
- **SQLite 单文件、单权威服务**：规划书第八节说首版“单一权威服务和事务数据库”。写入由 SQLite 串行，适合小服测试（20–50 人）；扩到 2,000 注册要做压测，再决定是否换 PostgreSQL。
- **部署**：
  - 一台 Linux 服务器，前面用 Caddy 做 TLS；
  - Litestream 把 SQLite 持续备份到对象存储；
  - 恢复演练后再核账。
- **通胀监控以账本为主**：每一笔发行都按来源记账，审计按来源列出。定案复核发现，玩家每天买一份篮子后，价格线挡不住小额凭空发币，所以价格线只作辅助。

## 还缺什么（按上线顺序）

1. **App 要改用这个驱动器**。现在 App 的教会系战斗在 `ChapterOneTestView` 里自己排敌人出手，部分时机来自 Unity 回调，和服务器复算不保证一致。要做两步：
   - 先把 App 的现行规则逐条搬进 `MPCChurchBattleStepper`；
   - 再让 App 由 stepper 推进，Unity 只负责表现，并记下操作记录。

   见 [Codex 任务单](../CODEX_TASKS_SHARED_SERVER_M0_20260929.md)。在此之前，服务器复算的是调参模型的时机，不是手机上的时机。
2. **主线 Q1–Q30 的战斗不在复算范围内**：各关有专门的出手节奏，要另做。共享服首批只开教会系战斗即可。
3. **共享服角色**：现在服务器上的角色是“某层塔的推荐配装”，由运营工具设置，不是玩家的真实成长。共享服的角色成长、配装和遗落物所有权要另做。
4. **登录与安全**：
   - 现在是建号时发的令牌。正式要接 Sign in with Apple 或 Game Center。
   - 服务前面要加 TLS 和限流。
   - 运营令牌只能在内网用。
5. **按天放开**：服务器还没限制每天的塔层。开放塔层前要接 `MPCDailyPacing`。
6. **运维**：备份与恢复演练、恢复后再核账、按功能暂停开关、压测（规划书首个压测候选是 200 人同时在线）。
7. **经济数值已于 2026-09-30 代定**（[共享服经济判定](../shared-economy-decisions-20260929/README.md)“定案”一节）：
   - 保留 24/12，共享服每日玩法付单机的 15%；
   - 本地铜最多计 12,000，按 15% 折算；
   - 交易费 5% 进城市预算；
   - 公共目标奖励 12 铜。

   城市预算创世 10 万只是小样的占位数。正式的城市预算来自 NPC 销售的收费，要等 NPC 经济接进服务端。
